# Obsidian VS Code Workbench

Obsidian desktop plugin that opens every text file in a real VS Code editor (via `code serve-web`) with a VS Code-style bottom terminal drawer.

Status: in development (a spike with one ribbon icon and one Code tab, the server lifecycle, the settings tab, and the Code tab opening every text file in the vault; see `docs/spike-decision.md`). Not submitted to the community store.

## Network use

On first use the plugin downloads the VS Code server from Microsoft, after you accept its licence terms. The first Code tab you open shows the licence modal; nothing is downloaded or started until you accept, and declining (or pressing Escape) opens the file in your system's app and asks again next time. The server runs only while you use it: it stops when Obsidian quits (with unsaved Code buffers it first asks you to save them all or discard them, and asks again if something is still unsaved, such as a new file without a name; there is no Cancel on that prompt, because Obsidian closes the window after its quit tasks finish and a Cancel could not stop that, so it would only lose the edits; Escape saves), or after 5 minutes with no visible Code tab and no unsaved buffer, and a server left over from a crash is cleaned up at the next start (a pidfile in the plugin's `.server` folder lists only process ids, never the token). When a start fails, a notice names the reason and any Code tab that was still showing the stopped server's page is closed rather than left blank (a tab with the crash banner stays, so its Restart can try again). If the download fails, the plugin looks up `update.code.visualstudio.com` and opens a TCP connection to its port 443 (no request is sent) to tell an unreachable network from another failure, because `serve-web` itself does not say why. The server is pinned to the installed VS Code build's commit (`--commit-id`), so later starts do not ask Microsoft for a newer one. Apart from that download, the plugin talks to `127.0.0.1`: the local `serve-web` server, bound to loopback with a connection token passed through a mode-0600 token file (never on the command line). The plugin adds no telemetry or analytics, and VS Code telemetry, extension auto-update and update checks, and experiments are switched off. Two kinds of request to Microsoft remain that cannot be switched off: on each load the workbench fetches two small static configuration files from `main.vscode-cdn.net` and sends one marketplace query for the single extension id `github.copilot-chat` (it does not send your installed extensions) (`docs/spike-decision.md`, "Outbound connections").

Without trust, VS Code opens a folder in Restricted Mode and the Python extensions stay inactive until you click Trust. VS Code stores that answer per origin, and the origin includes the server's port. The plugin keeps one loopback port per vault (`stablePort` in `data.json`) and tries it first at every server start, including the restart after the 5-minute idle stop, so the answer survives restarts (measured: same origin, no Restricted Mode after a restart, in `docs/spike-extensions.md`). If something else holds that port, the server starts on a free port for that start, the stored port is kept, and the Extensions section in settings says so. By default (setting "Trust the vault folder", `trustVaultFolder` in `data.json`, on) the plugin also writes VS Code's Workspace Trust record for the vault folder, and only that folder, into the Code tab's browser storage at every tab load before the workbench starts, so the tab opens trusted with no click, on a fallback port too. It does not clean up old records: the browser keeps one database per origin, so the record a server on another port left behind sits in that origin's own database, which the seed (it runs in the current server's origin) cannot reach, and it stays there. Such a record is inert (it only applies to that exact origin) and a later server on that port reseeds its own entry. The seed's script still drops entries for other loopback ports that it finds in the current origin's database, and never one for a port a running server holds or when the held-ports list is empty; in a real profile it finds none. Workspace Trust itself stays on, and a folder other than the vault opened on the same server stays untrusted. With the setting off nothing is written (a record already stored is left alone) and the Restricted Mode banner returns at the next tab load; trust the folder yourself with "Workspaces: Manage Workspace Trust", then Trust. If the seed does not take (VS Code changed how it stores the record), the tab still opens in Restricted Mode and the settings tab says so and names that command (`docs/spike-extensions.md`, Trust record).

The ribbon icon opens the active file when it is one that opens in a Code tab (see "Which files open"); for a note, canvas, base, PDF, image or any other file Obsidian opens itself, it opens the file named by `spikeFile` in the plugin's `data.json` (a vault-relative path, hand-edited), then the built-in spike file.

## Which files open

Nothing is registered by hand. When the plugin starts, and again whenever a file is created or renamed (and when the window regains focus, at most every 30 seconds, for files made outside Obsidian), it walks the vault folder on disk and registers every file extension it finds against the Code tab, in small slices so the window stays responsive. It walks the disk rather than asking Obsidian's file index because, with "Detect all file extensions" off, Obsidian does not list a `.py` or `.zig` file until its extension is registered. The registered set is written to the developer console (`VS Code Workbench: registered extensions (...)`).

- **Hidden:** the contents of `.obsidian`, `.git` and `node_modules` are never scanned or opened.
- **Open as text:** code files, dotfiles, and `svg`, `csv`, `txt` and `json`.
- **Never in a Code tab:** Markdown, canvas and base files, and binaries (images, pdf, archives, audio, video, fonts, executables and the like). Obsidian's own views handle them, and their extensions are never passed to the registration call.
- **Your exclude list** (settings) is never registered.
- **A symlink loop, a broken link or an unreadable folder** is skipped with a console warning; the scan carries on. Links to folders are followed once.
- **Size and binary guard:** a file over 2 MB (2,097,152 bytes opens, one byte more is refused), or with a null byte in its first 8 KB, is refused with a notice and opened in your system's app. A file over the limit is never read; otherwise only the first 8 KB is.
- **Other editors:** if Code Files, VSCode Editor, Code Workbench or any other plugin already owns an extension, this plugin leaves that extension alone and shows a notice naming the owner (one notice per extension per session, listing the extensions that one owner keeps). It only reads the view registry and never changes another plugin's registration or settings. An extension Obsidian itself opens (`svg` is shown by its image viewer) is left alone without a notice. To use Code tabs for a refused extension, turn the other plugin off and reload.
- **One tab per file:** opening a file that already has a Code tab (from the explorer, quick switcher, a link, a split or another pane, even twice in quick succession) focuses that tab instead of adding one.

### Extensionless files and dotfiles

Obsidian opens files by extension, so `Makefile`, `Dockerfile`, `.env` and `.gitignore` have nothing to register. As a best effort, a plain click on such a file's row in the file explorer is taken over and opens in a Code tab (a shift-, ctrl-, cmd- or alt-click is left to Obsidian, so multi-select and open-in-new-tab still work on those rows). If the plugin is set to the fallback mode (`"extensionlessMode": "system-app"` in `data.json`), or Obsidian cannot make the tab, the file opens in your system's app with a notice. The other failures are handled in the Code tab's own open path and never leave a blank tab (never as a blank tab, in either case): a declined licence opens the file in your system's app, and a server that cannot start or a file that is refused (binary, over 2 MB) shows a notice naming the reason and opens no tab. The limit: this only sees rows Obsidian draws. Obsidian never lists dotfiles, and with "Detect all file extensions" off it does not list extensionless files either, so for those there is no row to click and nothing to intercept (turn "Detect all file extensions" on to see extensionless files).

## Working in a Code tab

A Code tab behaves like another Obsidian file view.

- **Saving.** Edits are saved by the chosen VS Code instance's own auto-save setting, copied at each server start (`files.autoSave` is written out as `off` when the instance sets none, because the web workbench would otherwise default to saving after a delay). With auto-save off, an edit stays unsaved until Cmd/Ctrl+S.
- **Closing with unsaved edits.** Closing a Code tab (the close button, Cmd+W, close all, close others, a tab in a background pane, a pinned tab) asks Save, Discard changes or Cancel, once per file. Save writes the file and closes; Discard closes and leaves the file on disk as it was; Cancel and Escape keep the tab open and focused. A clean tab closes with no prompt. With auto-save on, the tab waits a few seconds for the edit to reach disk before it asks. If the plugin cannot tell whether a tab has unsaved edits (the editor is still loading, or its page does not answer), it treats the tab as unsaved and asks. Navigating a Code tab to a different file from the explorer asks the same question; on Cancel the tab keeps its file and the new file opens in a new tab.
- **Rename and delete.** Renaming or moving a file in Obsidian makes the same tab follow it to the new path (title, embedded file, saved layout), with no second tab and no reload of other tabs. If the tab has unsaved edits the editor is not reloaded under them; the move is applied once they are saved. Because the editor's buffer stays bound to the old path until then, saving writes the edits to the old path (which brings that file back); the plugin then moves that text into the renamed file and removes the old path (within about a second of the save, and otherwise when the tab is shown again, closed, or Obsidian quits), and the editor reloads onto the renamed file. If the renamed file was changed by something else in the meantime nothing is overwritten: a notice says the edits are in the old file. Discard moves nothing and leaves both paths as they are. Nothing is moved either when another file has taken the old path (one made there in Obsidian, one renamed onto it, one already there when the rename happened, or another tab opened on it): a notice says that saving from the tab writes to the old path, and the renamed file and the other file are left alone. The move only happens for a save the plugin saw the tab make: it looks at the tab (every second while a renamed file's edits are pending, and when the tab is saved, shown or closed, and at quit) and counts a save when the buffer goes from unsaved to saved while the old path's file changed. A file made at the old path outside Obsidian (a shell, `git checkout`) is therefore never moved over the renamed file, even if the edits are later undone: a notice says anything saved from the tab is in the old path. The save is also only carried while the old path is still the file that save wrote (its size, modification time and inode are recorded when the save is seen): if anything writes the old path afterwards, whether a shell, `git checkout` or a new file with the old name, nothing is moved and the same notice appears. If a save is made and the tab is closed before the plugin's look can see it, or the editor cannot be read at the look that would have seen it, the same notice appears and the edits stay in the old file. One gap remains: if something writes the old path and the edits are then undone, both within one second (the look interval), the plugin cannot tell that write from a save and would move it. A rename to a name a Code tab does not open (`.md`, a canvas, a base, a binary extension, an excluded extension) closes the tab through the unsaved-changes prompt. Deleting a file in Obsidian closes its tab at once, with no prompt, since there is nothing to save to. A file deleted outside Obsidian (a `git checkout`, another tool) closes a clean tab; a tab with unsaved edits stays open and VS Code shows its own deleted-file state.
- **Changes on disk.** When a file changes on disk while it is open (a `git checkout`, another tool), VS Code in the tab decides what happens; the plugin adds no prompt of its own, does not watch the file and never overwrites the editor's text. Checked against a real VS Code web server (`npm run check:workbench`, auto-save off): a tab with no unsaved edits reloads the new text silently (VS Code shows no reload prompt for that); a tab with unsaved edits keeps its text and the file on disk keeps the outside change; and saving that tab is refused by VS Code ("Failed to save: The content of the file is newer", with Compare and Overwrite buttons) and writes nothing until Overwrite is chosen.
- **Hidden chrome.** The activity bar, status bar, title bar and command centre are hidden by workbench settings the plugin writes into its own folder at every server start (and lays over the browser profile's settings on every load, so a setting copied from your instance cannot bring them back). The side bar and the panel have no settings switch, and the secondary side bar did not hide on the VS Code version measured (`docs/spike-decision.md`, `chrome: visible`), so those stay visible: the tab shows part of VS Code's chrome. Hiding is best effort and never stops a tab from opening; a settings file that is missing or corrupt is rewritten.
- **Theme.** The tab follows Obsidian's light or dark mode (the `theme-dark` class on the page, so custom themes map too) with VS Code's Dark Modern and Light Modern themes. When Obsidian's mode changes, open tabs switch in place, without reloading the file or losing the cursor. `npm run check:workbench` loads a real workbench with the plugin's settings in each mode and measures the contrast of every syntax colour on the editor background: at least 4.5:1 in both (lowest 4.59 in light, 4.95 in dark, with the VS Code 1.144 themes).

## Terminal drawer

A strip runs along the bottom of the Obsidian window on desktop. Over a Code tab it is always there; over a note, canvas, graph, PDF or any other view it follows the "terminal drawer over non-code views" setting (on by default). Click it, or run "Toggle terminal drawer" (default hotkey Ctrl+`, rebindable in Obsidian's hotkey settings), and a drawer slides up with one shell. It needs no Code tab and no VS Code server. It does not exist on mobile.

- **Shell.** Created on the first reveal, in the folder of the active file (the vault root when there is no active file, the view has no file, or the folder is gone). It then keeps that folder and stays alive when you switch files or hide the drawer. A shell that exits shows an "exited" line and a Restart shell button on its tab; the tab stays until you close it.
- **Tabs.** One tab per shell, named after the shell and a number (`zsh 1`). **+** adds a shell in the active file's folder and shows it; clicking a tab shows that shell without restarting anything or clearing its scrollback. The trash button ends the active shell: it asks first when the shell is running, and not at all for one that has exited or never started. Cancel and Escape keep it. Killing a tab shows the next one. Killing the last shell closes the drawer and leaves the strip; the next reveal starts a fresh shell. A shell that ends by itself keeps its tab and the drawer open.
- **Layout.** The drawer spans the main pane area only; the sidebars keep the full window height, and the main pane area is shortened by the drawer's height. Collapsing a sidebar or resizing the window re-flows the drawer. The status bar moves up only when the drawer reaches the bottom-right corner (right sidebar collapsed).
- **Non-code views.** With the setting off, the strip, the drawer and the hotkey are gone over notes, canvas, graph and PDF alike (the hotkey does nothing there), and a Code tab keeps all three. Turning it off or on takes effect at once and never closes the drawer or ends a shell: switch back and the same tabs, scrollback and open state are there.
- **Status bar.** "1 shell" / "N shells" counts shells that are running. It shows whenever one runs, whatever the setting and whether the drawer is open, and goes at zero. An exited or failed shell is not counted.
- **Size.** Drag the top edge. The height is at least 120 px and at most the window height minus 160 px, when dragging and when restored. Height and open state are saved per device in `data.json` under `drawer`, keyed by a device id kept in Obsidian's local storage (not in the vault).
- **How it works.** The terminal is xterm.js. The shell runs behind a small Python helper (`src/terminal/pty_helper.py`, standard library only, bundled into `main.js` and written to the plugin's `.server` folder) that provides the pseudo-terminal. The plugin talks to it over stdin and stdout pipes only: no socket, no network, no native module. It needs `python3` on your PATH. If `python3` is missing or is the macOS Command Line Tools placeholder, or the shell is missing or not executable, the drawer shows a red message naming the problem, and the tab's Try again button tries again. The placeholder is never run (running it opens an install dialog).
- **Hotkeys inside a Code tab.** VS Code's page swallows keys, so Obsidian's own hotkeys do nothing while it has focus. The plugin runs a small script inside the page that watches for exactly two chords, the ones Obsidian has for "Toggle terminal drawer" (default Ctrl+`) and the quick switcher (`switcher:open`, default Cmd+O), and reports only the action's name back to the plugin. It never sends the keys or any text typed, and opens no connection. A bridged chord is consumed (no backtick typed, no VS Code Open File); every other key goes to VS Code untouched, and holding a key acts once. The chords follow Settings > Hotkeys within about a second, and the old chord goes back to VS Code. A chord is matched by the character the key types; when Alt/Option is held (on macOS Alt+O types "ø") or the layout makes the key dead, the key's US-layout position is used instead, for letters, digits and the backtick. Inside the terminal the close key is the same live hotkey, so a rebinding applies there too. The bridge works in the webview embed (the default). In the iframe embed mode a Code tab gets no page script and so no bridge: the hotkeys do nothing while the editor has focus there, and the strip and the command hotkey outside the editor are what is left. Opening the drawer this way moves keyboard focus into the terminal; hiding it returns focus to the editor. The bridge is switched by the recorded spike decision (`hotkey_bridge` in `docs/spike-decision.md`, `HOTKEY_BRIDGE` in `src/hotkey/decision.ts`); with `no` it is not installed and the strip and the hotkey outside the embed are what is left.
- **Cleanup.** Quitting or disabling the plugin hangs up every shell and everything it started. The helper is in the child registry, so the startup orphan sweep removes one left by a crash.

## Settings

Open Settings, Community plugins, Workbench. Every time the tab opens it rescans, shows "Scanning…", then the list.

- **VS Code instance.** The scan reads `/Applications` and `~/Applications` for VS Code, VS Code Insiders, VSCodium, Antigravity and Antigravity IDE. A build is classified by its bundle identifier (`Info.plist`, else `product.json`), never by its folder name, and is listed only if its command-line tool passes `serve-web --help` (exit 0, output mentions `serve-web`, 5 seconds; run directly, never through a shell). The check starts no server, opens no port and downloads nothing. The default is the newest VS Code build (stable or Insiders, by version number); a build you pick is kept, and if it later disappears or fails its check the tab says why and uses the default until you pick again (the saved choice is not rewritten). Changing the instance while a server runs does not stop it, so unsaved buffers are safe: the change applies the next time the server starts.
- **Custom CLI path.** An absolute path to a VS Code command-line tool. Verify runs the same check; a path that passes is listed as Custom.
- **Excluded file extensions, terminal drawer toggle, shell.** The exclude list is read by the extension scan (see "Which files open"); the toggle (read live by the drawer) and the shell are stored here for the terminal drawer. Extensions are entered without a dot; they are trimmed, lowercased and de-duplicated. An extension added to the list is not registered at the next scan; one that is already registered stays registered until Obsidian reloads. The shell defaults to `$SHELL`, else `/bin/zsh`.
- **Restart server.** Stops the server and starts a fresh one.

A hand-edited `codeCliPath` in `data.json` still overrides the instance chosen in the tab. A corrupt or partial `data.json` falls back to the defaults field by field.

### Your VS Code settings

At each server start the plugin copies the chosen instance's `User/settings.json` and `User/keybindings.json` (from its folder under `~/Library/Application Support`, for example `Code - Insiders`) one way into the plugin's own user-data folder, replacing the previous copy, and writes the workspace excludes on top: `.git`, `.obsidian`, `Attachments`, `node_modules` and `_to_delete` are excluded from `files.watcherExclude` and `search.exclude`, and win over the copied values. Comments and trailing commas in your `settings.json` are accepted; if it is invalid JSON, only the excludes are written and a notice says so. The VS Code server does not read those two files from its data folder, so the same copy is also written into the Code tab's own browser profile when the tab opens (once per server start; the excludes also go into the server's Machine settings, which it does read). Checked on a real server: a copied `editor.fontSize`, a copied keybinding and the excludes all take effect (`npm run check:user-data`). Edits made inside the embedded editor change the copy only and are replaced at the next start. The plugin never writes to, renames, deletes or changes the permissions of another instance's settings, extensions or app bundle, and it creates nothing in your vault outside its own plugin folder. The copy is private to you (mode 0600 in a 0700 folder) because settings can contain secrets.

### Microsoft-only extensions

Some extensions (for example Pylance, C/C++ and the Remote extensions) are licensed for Microsoft's own builds and may refuse to run in VSCodium or the Antigravity builds. The settings tab shows a one-line warning when the selected instance is not a Microsoft build. Nothing is done to work around the licence: choose VS Code or VS Code Insiders to use those extensions.

## Requirements

Desktop Obsidian 1.13.0 or newer, a local vault, and an installed VS Code (`code` with the `serve-web` command).

## Develop

```
npm install
npm run build      # type-check, then bundle to main.js
npm test           # vitest with a coverage report
npm run check:render     # the unsaved-changes prompts in headless Chrome, 4 window sizes, light and dark
npm run check:workbench  # real VS Code web server + headless Chrome: outside change to an open file, chrome hidden, colour contrast
```

`check:workbench` is not part of `npm test`. It needs the installed VS Code, Google Chrome and the VS Code server for the installed build's commit. Either point `CLI_DATA_SRC` at a `--cli-data-dir` whose `serve-web/` folder already holds that commit (it is copied, never written to), or set `ALLOW_DOWNLOAD=1` and `serve-web` downloads that server (about 600 MB) into a scratch folder. If neither fits it exits 2 before starting anything and names the commit it needs and the ones `CLI_DATA_SRC` holds. It exits 1 when a check fails and 2 when the check could not run (including a server that answers with an error, or a page that never paints).

The plugin folder goes in `<vault>/.obsidian/plugins/obsidian-vscode-workbench/` (`main.js` and `manifest.json`). Runtime files (token, server data) live under `.server/` inside it and are git-ignored.
